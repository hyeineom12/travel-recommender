# travel-recommender

동덕여자대학교 빅데이터(캡스톤 디자인) · 3인 팀

**개인별 제약이 다른 그룹을 위한 공정성 기반 여행 일정 생성 및 설명 시스템**

> 친구들이 각자 가고 싶은 곳과 예산·체력을 **비공개로** 입력하면,
> 아무도 무리하지 않으면서 모두가 자기 몫을 챙기는 일정을 만들고
> **왜 그렇게 됐는지 설명**해주는 웹 서비스.

데모 → https://hyeineom12.github.io/travel-recommender/

---

## 왜 만드는가

여행을 계획하면 한 명이 일정을 도맡고 나머지는 "아무거나"라고 답한다.
그러다 현장에서 불만이 나온다. 너무 걷는다, 돈을 많이 쓴다, 가고 싶던 곳이 빠졌다.

미리 말하지 않는 이유는 **예산과 체력이 말하는 순간 개인의 형편과 상태가 드러나는 정보**이기 때문이다.
적게 쓰고 싶다고 하면 궁색해 보이고, 못 걷겠다고 하면 민폐 같다.

> 문제는 서로의 취향을 **모르는 것**이 아니라 **말할 수 없는 것**이다.

일정을 만드는 도구는 이미 많다(Wanderlog, 트리플 등). 이 프로젝트는 **합의를 만드는 도구**를 목표로 한다.

자세한 배경과 평가 설계는 [`docs/캡스톤_주제안.md`](docs/캡스톤_주제안.md).

## 실행

```bash
cd web
npm install
npm run dev
```

http://localhost:3000 접속. **Node 18 이상** 필요.

### 검증 스크립트

```bash
cd web
node _test/run.mjs            # 5인 그룹 단위 검증 (제약 위반·꼭 반영)

```

## 배포

`main`에 푸시하면 GitHub Actions가 자동으로 빌드·배포한다.
워크플로는 [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml).

### 최초 1회 설정 (필수)

레포 → **Settings → Pages → Source**를 **GitHub Actions**로 변경한다.

기본값이 "Deploy from a branch"라서, 이걸 바꾸지 않으면 워크플로가 성공해도 사이트가 뜨지 않는다.

설정을 바꾼 뒤에는 자동 재배포가 걸리지 않으므로
**Actions 탭 → Deploy to GitHub Pages → Run workflow**로 한 번 수동 실행한다.

### 배포 확인

Actions 탭에서 상태를 본다.

| 상태 | 의미 |
| --- | --- |
| 초록 체크 | 성공. 1~2분 뒤 사이트 반영 |
| 노란 점 | 진행 중 (보통 2~3분) |
| 빨간 X | 실패. 해당 단계 로그 확인 |
| 워크플로 없음 | `.github/workflows/deploy.yml`이 푸시됐는지 확인 |

### basePath 주의

프로젝트 페이지는 `/<repo>/` 하위에 배포되므로 정적 파일 경로에 `basePath`가 필요하다.
워크플로가 `NEXT_PUBLIC_BASE_PATH=/travel-recommender`를 넣어 빌드한다.

`public/` 아래 파일을 `<img>`나 `next/image`로 직접 쓸 때는
**반드시 `asset()` 헬퍼를 거쳐야 한다.** 그러지 않으면 로컬에서는 보이고 배포 후 404가 난다.

## 알고리즘

### 1단계 · 선택 (`consensus.ts`)

```
1. 예산 하드 제약        각자 상한 중 최솟값을 그룹 기준으로
2. 거부 장소 제외
3. 각자의 '꼭' 먼저 확정   → 5명이면 5곳 확보
4. 나머지를 전략 점수 순으로
5. 예산·자리를 넘으면 → 옵션(원하는 사람만) 또는 제외
```

**개인 효용** = 직접 고름(0.85) 또는 (내 카테고리 취향 × 0.42 + 장소 매력도 × 0.38)
예산 비중이 크거나 체류가 길면 감점.

**취합 전략**

| 전략 | 목적함수 |
| --- | --- |
| 평균 | `max Σ util` |
| 최소 불만 | `max(min util)` × 0.8 + 평균 × 0.2 |
| 공정성 | `평균 − 0.7 × 표준편차` |

**만족도** = 선택 반영률 35% + 꼭 반영 30% + 예산 여유 15% + 체력 여유 10% + 거부 준수 10%

### 2단계 · 배치 (`schedule.ts`)

지역별로 묶어 일자를 배정하고, 시간 순으로 쌓으면서 매 시점에
(거리 + 식사 시간대 + 짐 무게)를 함께 보고 다음 장소를 고른다.

- 영업시간 창을 검사하고, 못 넣으면 제외
- 빈 식사 시간은 동선에서 가장 가까운 식당으로 자동 채움
- 걷는 거리와 대중교통 포함 총 이동거리를 분리 계산 (1.2km 초과 시 대중교통 가정)
- 쇼핑은 짐이 늘어나므로 하루 뒤쪽으로 밀림

### 3단계 · 설명 (`explain.ts`)

규칙이 산출한 근거를 문장으로 만든다.
실제 서비스에서는 이 구조화된 근거를 LLM에 넘겨 자연스럽게 다듬을 예정이며,
현재는 LLM 없이 검증 가능하도록 규칙 기반으로 구현했다.

**AI가 결정하지 않는다.** 장소 선정과 순서는 규칙이 정하고, AI는 빈칸 채우기·설명·대안 제시만 맡는다.

## 검증 결과

가상 그룹 500개 (3~6인, 2~4박)

| 전략 | 평균 만족도 | 최저 만족도 | 편차 |
| --- | --- | --- | --- |
| 평균 | 0.8910 | 0.7887 | 0.0590 |
| 최소 불만 | 0.8916 | 0.7914 | 0.0581 |
| 공정성 | 0.8906 | 0.7876 | 0.0594 |

| 조건 | 평균 만족도 | 최저 만족도 |
| --- | --- | --- |
| 부분 동행 허용 | **0.8906** | **0.7876** |
| 전원 동행만 | 0.8087 | 0.6968 |

**H1·H2(공정성 취합이 평균보다 낫다)는 지지되지 않았다.** 78승 78패로 사실상 무승부다.

**H3(부분 동행)은 강하게 지지된다.** 차이 0.082, 500건 중 443건에서 개선.
취합 전략을 바꾸는 것보다 20배 넘는 효과다.

> 공정성은 '누구를 우선할지 고르는 것'이 아니라
> '함께 갈지 말지를 유연하게 두는 것'에서 나왔다.

전략별 코어 구성이 달라진 그룹은 56.8%로 알고리즘 자체는 정상 작동한다.
기존 연구가 취합 전략에 집중해온 것을 반박하는 결과라, 논문 주장을 이 방향으로 잡는다.

## 협업 규칙

- `main` 직접 푸시 금지. feature 브랜치 → PR → 리뷰 1인 → merge.
- **작업은 시작할 때 Draft PR을 먼저 열고 assignee를 단다.** 누가 무엇을 잡았는지 보여야 3명이 겹치지 않는다.
  커밋이 하나도 없으면 PR을 만들 수 없으므로 빈 커밋으로 연다 — `git commit --allow-empty -m "작업 시작"`.
  끝나면 Ready for review로 전환한다. 문서 수정 같은 단발 변경은 예외.
- **이슈는 따로 만들지 않는다.** 논의가 이슈와 PR 두 군데로 흩어지면 한쪽이 방치되므로 PR 한 곳에 모은다.
- 브랜치명: `<타입>/<요약>` 예) `feat/search-filter`, `fix/map-marker`
- 커밋 메시지: 한 줄 명령형. 예) `추천 결과 카드 레이아웃을 추가한다`
- 비밀값(API 키, 계정 정보)은 커밋하지 않는다. `.env`는 gitignore한다.
