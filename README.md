# travel-recommender

동덕여자대학교 빅데이터(캡스톤 디자인)

## 협업 방식

3인 팀으로 진행한다. 아래 규칙은 팀 전원이 지킨다.

### 순서
**main pull → 이슈 → 브랜치 → 작업 → PR → 리뷰 → merge**

- 이슈 없이 브랜치를 따지 않는다.
- **착수할 때 자신을 이슈 assignee로 등록한다.** assignee가 비어 있으면 "아직 아무도 안 잡은 이슈"라는 뜻이다. 병렬로 움직이면 이슈가 없을 때 같은 작업이 겹친다.
- 이슈는 한 단계 크기로 쪼갠다. 여러 레이어를 한 이슈로 묶지 않는다.

### 브랜치
- **main 직접 푸시 금지.** feature 브랜치 → PR → **최소 1인 리뷰** → merge.
- 브랜치명: `<타입>/<범위>-<요약>`
  - 예) `feat/model-recommend-score`, `fix/data-null-handling`, `docs/readme-collab`

### 커밋 메시지
**영어 범위 접두어 + 한국어 명령형 한 줄.**

```
data: 관광지 원본 CSV 수집 스크립트를 추가한다
```

- 접두어는 폴더·브랜치 범위명과 같게 쓴다: `data:` / `model:` / `app:` / `docs:` / `repo:`
- 접두어만 영어인 이유는 grep·정렬·자동화가 걸리는 자리라서다. 본문은 한국어 그대로 쓴다.
- 리뷰어가 볼 것을 전제로 커밋을 작게 나누고 메시지를 설명적으로 쓴다.

### PR
본문에 아래 항목을 적는다.

- **범위** — 어떤 폴더/스택을 건드렸는가
- **바뀐 계약** — 데이터 스키마·인터페이스 변경이 있는가 (없으면 없다고 근거와 함께)
- **확인한 것** — 무엇을 어떻게 돌려 봤는가 (로그·출력 발췌)
- **점검** — 리뷰어가 봐 주었으면 하는 지점

하나의 PR은 하나의 범위를 원칙으로 한다. 불가피하게 관통하면 PR 본문에 명시한다.

### 이슈 라벨
- 범위 라벨은 폴더 이름과 같게 단다: `data` / `model` / `app`
- 성격 라벨: `task` · `documentation`
- 한 라벨이 두 폴더를 겸하지 않는다. **두 라벨이 붙으면 "관통 작업"이라는 신호**다.

### 문서
- 문서·주석·커밋 메시지는 **한국어**. 코드 식별자는 영어.
- 방향이 바뀌는 결정은 **코드보다 문서를 먼저 고친다.**
- 비밀값(API 키·토큰)은 절대 커밋하지 않는다. `.env`는 gitignore한다.
